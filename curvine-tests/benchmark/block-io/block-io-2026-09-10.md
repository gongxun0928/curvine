# Block I/O latency and throughput experiment — 2026-09-10

本次实现了小 block 远程读取的一次 RPC 路径。以提交 `39069ae2` 为基线，在同一台机器交替运行 release 二进制，逐字节验证数据。最终版本默认 128KiB chunk 下，4KiB 和 128KiB block 读取延迟分别降低约 54% 和 31–36%，4KiB 写入平均延迟基本持平。将现有 chunk 配置调到 1MiB 后，64MiB block 写吞吐提高约 38–49%，读吞吐提高约 120–135%；这部分主要来自配置调优。另探索了聚合 socket 发送，因真实 block 写入测试出现退化而撤回。

## 实现

1. `BlockReadRequest` 增加可选的 `read_once` 字段。远程 client 在逻辑 block 长度不超过一个 read chunk 时，将 open 和取数据合为一个请求。Worker 完成读取后释放文件及连接上的 handler，以 `Complete` 响应携带数据。Client 的 `complete()` 不再发送请求。
2. 老 client 不设置该字段，保留原协议；老 worker 忽略该字段、返回 `Open` 时，新 client 自动完成原有 read/complete 流程。EOF、seek 后重新取数、短响应拒绝、稀疏尾部补零和 short-circuit 路径都有验证。
3. 大数据原有 sendfile 路径保留；一次读取的小 block 使用拥有所有权的内存数据，以便在发送之前安全关闭文件。RPC 框架发送实现保持原样。

写入仍然保留 open/write/complete 和原有 flush/finalize，成功应答位置保持原样，也没有实现并行的在途请求。Master 元数据请求不属于本次优化范围。

后续源码核实：本次测量的普通文件后端使用 `std::fs::File::write_all/flush`，finalize 发布使用 rename，未在该生产路径调用 `sync_all/sync_data`。`File::flush` 在 Unix 上不是 fsync，因此这些写入数据不能解释成强制同步落盘的性能。这里保留的是既有提交语义；更强的断电持久性需要单独设计和验证。参见 [Rust File 实现](https://doc.rust-lang.org/src/std/fs.rs.html#1435-1450)。

## 测量方法

- 机器：80 个逻辑 CPU、40 个物理核、双 NUMA，约 186GiB RAM；主要比较固定在 CPU 2–5。
- Rust 1.92.0，release 构建，相同 Cargo.lock。Worker 使用 2 个 I/O 线程、4 个 blocking 线程。
- Client 和真实 Worker 通过 loopback TCP 通信，关闭 short-circuit，启用 sendfile。使用已知 block ID，包含连接池获取、block open、数据传输和 complete/finalize，不启动 Master。
- 存储分别使用 `/tmp` tmpfs 和工作区所在 `/dev/sda3` 文件系统。每次运行独立创建数据目录，成功后删除。
- 4KiB/128KiB 各 400 次有效样本、20 次预热；64MiB 各 16 次有效样本、2 次预热。默认每次写完立即读取，属于热缓存读取。校验全部字节；校验耗时不计入读延迟，校验带来的缓存/调度影响仍属于工作负载。
- 最终版本在 tmpfs 和磁盘目录各做 3 轮，每轮交替 baseline/optimized 顺序。下表是各轮平均耗时/吞吐的中位数；p99 也取各轮 p99 的中位数，并非合并样本后的 p99。
- 更改 chunk 时，两边同时设置相同值。read-ahead 和 drop-cache 范围仍为 1MiB，以便单独观察 chunk 的影响。
- 原始每轮 CSV、二进制 SHA256、摘要和测试结果在 [results](block-io-2026-09-10-results/)。`selected-*` 是最终版本，`gather-*` 是已撤回的聚合发送实验，`read-only-ablation-*` 是中间拆分实验，`frame-runs.csv` 是纯传输微基准。这些是每轮统计值，未保存每次 I/O 的独立时间序列。

## 同配置比较：代码本身的收益

默认 chunk = 128KiB：

| 存储 | 操作 | baseline 平均延迟中位数 | optimized | 变化 |
|---|---|---:|---:|---:|
| tmpfs | 4KiB 读 | 122.199µs | 55.794µs | −54.3% |
| 磁盘目录 | 4KiB 读 | 120.818µs | 55.242µs | −54.3% |
| tmpfs | 128KiB 读 | 159.909µs | 102.694µs | −35.8% |
| 磁盘目录 | 128KiB 读 | 148.587µs | 101.872µs | −31.4% |
| tmpfs | 4KiB 写 | 152.036µs | 151.651µs | −0.3% |
| 磁盘目录 | 4KiB 写 | 166.504µs | 166.208µs | −0.2% |
| tmpfs | 128KiB 写 | 217.692µs | 209.221µs | −3.9% |
| 磁盘目录 | 128KiB 写 | 266.353µs | 264.458µs | −0.7% |

4KiB 读的 tmpfs p99 从 145.250µs 降至 68.326µs，磁盘目录从 137.855µs 降至 66.115µs。请求数测试确认，新 client + 新 worker 的正常小 block 读取为 1 次，旧 worker 回退为 3 次。64MiB block 的相同配置吞吐变化不足 1%，没有大 block 代码加速结论。

机器存在调度噪声。最终 tmpfs 的 4KiB 读每轮均值范围，baseline 为 119.791–124.712µs，optimized 为 53.937–58.486µs；此前探索轮次曾出现明显慢样本。因此不把几个百分点的变化视为稳定收益，也不承诺每次请求都更快。最终版本未改写入实现，写入均值的小幅变化作为工作负载/测量波动保留。磁盘目录 4KiB 写 p99 为 183.538→200.103µs，不能由均值持平推断尾延迟也持平。

### 撤回聚合发送的依据

初版还将 `RpcFrame`/`WriteFrame` 的协议头、业务头、内存数据改为 `write_vectored`，避免复制 payload，处理 partial write、Pending、Interrupted 和错误。磁盘目录交替读写时，4KiB 写入平均延迟为 168.195→182.258µs（慢 8.4%）。仅保留 `read_once`、恢复原始 RPC 发送方式的 3 轮拆分实验中，4KiB 写入为 173.259→167.258µs，4KiB 读取为 125.590→55.550µs。

随后用 `--separate` 先连续写入再读取，聚合发送版本 4KiB 写入仍为 166.260→183.159µs（慢 10.2%），128KiB 写入为 274.417→293.520µs（慢 7.0%）。因此未采用聚合发送；最终版本重新执行上述完整 A/B 比较。实验补丁以 [独立 patch](block-io-2026-09-10-results/experimental-gather-send.patch) 留存，未应用到当前生产代码。`--separate` 在大 block 场景最多暂存 4 个 block，以控制容量。

## Chunk 调优：减少大 block 的逐块往返

比较原始版本的默认 128KiB chunk 与优化版本的 1MiB chunk：

| 存储 | 64MiB block | baseline 128KiB | optimized 1MiB | 吞吐变化 |
|---|---|---:|---:|---:|
| tmpfs | 写 | 1070.441MiB/s | 1594.837MiB/s | +49.0% |
| 磁盘目录 | 写 | 848.500MiB/s | 1173.202MiB/s | +38.3% |
| tmpfs | 读 | 1575.746MiB/s | 3699.985MiB/s | +134.8% |
| 磁盘目录 | 读 | 1799.672MiB/s | 3960.414MiB/s | +120.1% |

原始版本只改成 1MiB chunk，磁盘目录也能达到 1166.339MiB/s 写、3965.556MiB/s 读，说明这一部分收益主要来自已有配置。64MiB block 的 open + 数据 + complete 从 `2 + 512 = 514` 次请求/响应减少到 `2 + 64 = 66` 次，仍然逐块应答。

可将 [1MiB 配置片段](block-io-1mib.toml) 合入目标 client 的现有配置。没有修改全局默认值或机器上运行中服务的配置。默认 8 个 chunk 的上层队列在调大 chunk 后，潜在数据缓冲容量从约 1MiB 增至 8MiB；本基准直接调用 block client，未测量完整文件缓冲层的高并发内存开销。

## 已撤回聚合发送的独立微基准

`frame_bench` 只测 frame 请求/响应，不含存储。5 轮中位数：

| 数据大小 | 方向 | 原平均延迟 | 聚合后 | 吞吐变化 |
|---|---|---:|---:|---:|
| 4KiB | 写请求 + ACK | 24.142µs | 21.151µs | +14.1% |
| 4KiB | 读请求 + 数据响应 | 26.232µs | 21.032µs | +24.7% |
| 128KiB | 写请求 + ACK | 51.146µs | 44.987µs | +13.7% |
| 128KiB | 读请求 + 数据响应 | 53.112µs | 47.381µs | +12.1% |

这些结果支持减少发送调用的效果，但完整 block 测试暴露了不同结果，因此没有把微基准收益作为保留改动的依据。

## 复现

在原始提交和优化代码的两个独立 checkout 中，放入完全相同的 `curvine-worker/examples/block_io_bench.rs`，分别构建并保留二进制：

```sh
RUSTC_WRAPPER= cargo build --locked --release -p curvine-worker --example block_io_bench
```

在当前 checkout 运行比较脚本，输出目录必须尚不存在：

```sh
python3 build/tests/benchmark_block_io.py \
  --before /tmp/curvine-rpc-perf-results/block-grouped-before \
  --after /tmp/curvine-rpc-perf-results/block-selected \
  --output /tmp/block-io-recheck --data-dir /tmp \
  --cpus 2-5 --rounds 5 --chunks 131072,1048576
```

`--data-dir` 换成待测文件系统中的目录；加 `--separate` 可分开读写阶段；`--sendfile 0` 可测试 buffered response 路径。每次运行只操作其新建的独立目录。当前机器上的二进制路径用于本次复核；其他机器需重新构建。

## 后续方案与适用范围

已经验证的是单连接、loopback、已知 block 的远程数据路径，磁盘目录读取也是写后的热缓存读取。没有测跨机器网络、冷盘、Master 元数据、高并发、多副本或 FUSE 的端到端性能，因此不据此直接更改全局参数。

下一步小 block 写入可以设计携带完整数据的 `PutBlock`，在服务端一次请求内部执行 open/write/finalize；必须一起设计提交应答丢失时的幂等重试、部分失败清理和副本完成语义。它能减少 4KiB 写入的三个阶段，16MiB 帧上限不阻止这一设计。

大 block 的进一步方向是有界的多 chunk 在途窗口、首块携带 open、末块携带 finalize。gRPC streaming 也能在一个 RPC 生命周期内传多个 message，但 message 数、RPC 数和串行等待次数不同；逐 message 等待 ACK 仍会限制吞吐。现有 orpc 可以先实现相同的数据流控制语义，再依据跨机器结果决定是否迁移传输框架。
